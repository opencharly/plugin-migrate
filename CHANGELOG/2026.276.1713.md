# 2026.276.1713 — feat(migrate)!: rewrite the legacy kind:pipeline grammar into lobster steps syntax

## Summary

`plugin-migrate` gains the **third transform** of the workflow wave: `charly migrate` now rewrites the retired `kind:pipeline` grammar into lobster `steps:` syntax. Without it every pipeline in the org fails to load after the cutover, because the loader no longer accepts the old keys.

The rewrites, all asserted by the bed:

| old | new |
|---|---|
| `stages:` | `steps:` |
| `kind: command` + `command:` | `run:` |
| other `kind:` + fields | single-step sugar `<word>: {…}` / `plan: [{<kind>: {…}}]` |
| `skip_when: X` | `when: !(X)` |
| `@stage.out` | `$stage.json.out` |
| `$pr` / `$env.N` | `${pr}` / `${env.N}` (the ref must be brace form to expand), with `args:` declaring `pr` |
| top-level knobs (`concurrency.lanes`, …) | consolidated into `config:` |
| — | a required `description: Migrated pipeline <name>.` |

Two things it deliberately does **not** touch: the `@github` candy refs, which stay byte-identical (they are loader refs, not variables — pinned by a byte-stability test), and legitimate local shell variables such as `$latest` and `$b`, which stay exactly as written. The transform is **idempotent** — it fires only on a body that still has `stages:`, so a second run reports `nothing to migrate`.

**The lifted verb is self-contained.** Because `kind:pipeline`'s stage bodies become ordinary `verb:` providers, an entity-level knob (`skills:`, `llm:`, `repo:`, `media:`, `report:`) would otherwise be lost to a lifted verb that has no pipeline config around it — so the transform **duplicates** each verb's knobs into its own body. That is the part a reader is most likely to misread as over-eager, so the unit tests pin it (the bed asserts `skills:` ×5, `report:` ×4, `media:` ≥2, `repo: omacom/omarchy` ≥5).

**Consumer obligation, stated because it is invisible in the diff:** the migration must be run before a wave-`charly` loads a project, which is the `eval-omarchy` leg of this wave. Nothing else changes for a consumer: the CLI, the flags and the `version:`-stamp behaviour are untouched.

### 4. Bed provenance — how a *compiled-in* plugin is exercised from a worktree

`plugin-migrate` is **compiled into charly** (`charly/plugins_generated.go`: `cp_plugin_migrate "github.com/opencharly/plugin-migrate/candy/plugin-migrate"`), and the bed's own description says it: *"the host charly resolves `command:migrate` from the compiled-in registry and `Invoke(OpRun)` runs the engine in-proc."* So the code under test is whichever `plugin-migrate` the **charly binary** was built with — and the two documented dev-tree override knobs do **not** reach it, which was verified rather than assumed:

```
$ CHARLY_PLUGIN_DIR=/tmp/wfir/plugins /tmp/wfir/mig/bin/charly check run check-migrate-local
# → still runs the charly-pinned v0.2026272.332 engine: the fixture reports "nothing to migrate",
#   because that release has no pipeline transform. CHARLY_PLUGIN_DIR loads BAKED/out-of-process
#   plugins from a word manifest (discoverBakedPluginWords); a compiled-in plugin is not reloadable.

$ CHARLY_REPO_OVERRIDE="opencharly/plugin-migrate=$PWD" …
# → same result: spec/proc.RepoOverrideDir redirects a repo CLONE, not an already-compiled package.
```

The mechanism that does reach it, and the one used for every artifact above: a **temporary, uncommitted** `replace` in the charly worktree's `go.work`, then a direct build.

```
$ cd .worktrees/workflow-ir/charly
$ git diff -- go.work
+// TEMPORARY dev-tree override — NOT to be committed (verify-before-push).
+replace github.com/opencharly/plugin-migrate/candy/plugin-migrate => …/.worktrees/workflow-ir/plugin-migrate/candy/plugin-migrate
$ GOWORK="$PWD/../go.work" go build -buildvcs=false -ldflags "-X main.BuildCalVer=2026.276.9999" -o /tmp/wfir/mig/bin/charly .
$ git status --porcelain
 M go.work
```

**The `replace` was never committed and is reverted before this branch is pushed** — it exists only to make the worktree's plugin the one the binary carries. `${CHARLY_BIN}` inside the bed stamped the active binary, so what ran is exactly the head above. The bed remains the fresh-rebuild gate (Step 4 of the sequence is a real `charly update`), and the tree it was built from is the committed one.

**Routed to a named task, not parked — `opencharly/charly#775`** (filed and claimed by this session, with the full evidence in it): this dev-tree path is the *only* way to R10 a compiled-in plugin from a worktree today, and `CHARLY_PLUGIN_DIR`/`CHARLY_REPO_OVERRIDE` do not cover the compiled-in case. `#775` is the named owner of the exit — it decides and documents ONE sanctioned mechanism (either a first-class compiled-plugin override consumed by `pluginsgen`/`bootstrap-charly.sh`, or the `go.work` `replace` written into the rulebook with a matching Standard-8 amendment in `beds-and-r10.md`). It is deliberately **not** patched in-tree here: the mechanism lives in `charly`'s `pluginsgen` + `bootstrap-charly.sh` and in the `check` skill's Standard 8, neither of which is a file this repo owns, and patching either from a plugin-migrate PR would be exactly the cross-repo workaround R4 forbids.
