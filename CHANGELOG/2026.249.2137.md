# 2026.249.2137 — migrate: unroll the targetless deploy group: node into the member-tree bed shape (Cutover C task 1)

## Summary

The `charly migrate` engine gains the group-kind-removal consumer half (Cutover C task 1): a new migration-table row **`unroll-group-deploy`** (pinned at the schema head `2026.249.2125` — the head bump is spec #106, tag v0.2026249.2129) rewriting an authored targetless `group:` deploy node into the post-migrate member-tree bed shape:

- the **FIRST member** (document order) becomes the **deploy primary** — the entity keeps its name and gains the member's substrate-kind discriminator; the member's own key is consumed;
- the **group scalars** (disposable / lifecycle / description / iterate — every group-body field has a #Deploy-body home) **move onto that primary's kind body**, the member's own keys winning on collision (the group body was the default, the member the override);
- the **REMAINING members** stay deploy-level siblings, verbatim;
- **nested groups rewrite recursively** (post-order — a nested group converts before its enclosing entity);
- the rewrite is **IDEMPOTENT** (a second run is a no-op — the migrated spelling carries no `group:` key);
- a **DEGENERATE group** (no promotable member, or a first member without exactly one mapping-valued kind discriminator) is left untouched — the load-time gate then names the node; the hook never guesses a primary.

The step is an `apply:` reshaper hook (`unrollGroupDeploy` in `reshape_group_deploy.go`) — the sanctioned conspicuous path, since none of the four key-transform ops can replace two sibling keys with one promoted pair. Per the plan, hand-edits of group: configs are NOT the path — `charly migrate` is. Pins move to the settled contracts: spec v0.2026249.2129, sdk v0.2026249.2114.
