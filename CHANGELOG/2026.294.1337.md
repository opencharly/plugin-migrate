# 2026.294.1337 — feat(migrate): carry a retired `concurrency: {lanes: N}` onto the pooled fan-out arm

## Summary

`charly migrate` used to flatten the retired pipeline-level `concurrency: {lanes: N}` into `config: {lanes: N}` — a key nothing reads (`sdk/workflowkit` has zero `Config` occurrences; plugin-pipeline#37/#43). The document loaded and the fan-out was silently gone: the deleted executor's `runBatch` was a worker pool of N over the run's PR list, every stage run once per item, ANY failed lane failing the run.

The reshape now carries that knob onto the new grammar's loop arm. For a stage graph the target grammar can express, the whole migrated step list is wrapped in ONE lane step:

```yaml
- id: lane
  lanes: ${prs}
  batch_size: 16
  item_var: pr
  steps: [<the migrated stage list>]
```

Three decisions, each measured rather than assumed:

- **No seed step.** The collection is the run's `prs` ARG. `#WorkflowArgVal` admits a flat list (spec#262), `plugin-lobster`'s `resolveLoopItems` parses a templated (non-ref) operand as JSON, and `renderTemplateValue` renders a non-scalar as JSON — so `--args-json '{"prs":["a","b"]}'` feeds `lanes: ${prs}` directly. The `--prs a b c` flag it replaces was deleted with the executor (`grep -rn '"--prs"' --include=*.go` → 0 hits), so a seed step would have invented a second, hand-written input channel for no gain.
- **`$pr` becomes `$pr.stdout`, not `${pr}`.** The loop variable is a SCOPED STEP RESULT; `${…}` reads ARGS ONLY (`refs.go`), so the arg spelling would read the wrong thing in every lane. `.stdout` is the field a string item lands in (`createSyntheticStepResult`), which is what a `#WorkflowArgVal` list holds.
- **The arm is emitted only where the gate accepts it.** `workflowkit.ValidatePipeline` validates a loop body's sub-step references against the pipeline's TOP-LEVEL step ids, so a lane body whose stages reference each other is refused at load even though the engine runs it (`batch.go` accumulates `scope[sub.Id] = res`). That is `opencharly/sdk#441`. For such a graph the knob keeps the one loadable home it has — `config:` — and the un-restored fan-out is recorded on #23; emitting the arm anyway would reproduce exactly the defect #20/#22 were about.

On the consumer that splits cleanly: `check-omarchy-accept-matrix` (two ref-independent command stages) wraps; `eval-pr-plan` (twelve stages chaining `@oracle` → `render`/`control`/`eval`/`gate`/`report` → `record`) does not.
